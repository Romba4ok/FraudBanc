# Risk Ledger — локальный анализ риска мошенничества

Risk Ledger — локальное веб-приложение для анализа банковских CSV-файлов. Модель CatBoost оценивает вероятность мошенничества для каждой записи, выводит наиболее подозрительные записи первыми и показывает факторы, повлиявшие на оценку.

Все вычисления выполняются на вашем компьютере. Для работы приложения не нужны облачные сервисы, внешняя база данных или передача CSV третьим лицам.

> Оценка модели — сигнал для дополнительной проверки, а не доказательство мошенничества и не основание для автоматического решения по клиенту.

## Возможности

- загрузка CSV размером до 150 МиБ;
- автоматическое определение разделителя `;` или `,`;
- работа с файлами как с целевой колонкой `GB_flag`, так и без неё;
- ранжирование записей по вероятности риска;
- уровни риска: низкий, средний, высокий и критический;
- SHAP-объяснение основных факторов для каждой записи;
- фильтрация результатов и изменение порога проверки;
- расчёт метрик качества, если в CSV присутствует корректный `GB_flag`;
- отдельные разделы «Обзор», «Рискованные записи», «Качество модели» и «Качество данных»;
- скачивание полного результата и отдельной выборки для ручной проверки в CSV;
- простой и экспертный режимы объяснений, комфортная и компактная плотность;
- повышенный контраст и масштаб текста до 200%;
- локальное временное хранение данных только на время сессии.

## Быстрый запуск через Docker

Это рекомендуемый способ запуска. Понадобится только Docker Desktop с поддержкой Docker Compose v2.

Для анализа больших файлов рекомендуется выделить Docker Desktop не менее 4 ГБ оперативной памяти.
При первой сборке Docker потребуется доступ в интернет для загрузки базовых образов и зависимостей. Загружаемые банковские CSV при этом обрабатываются только локальными контейнерами.

### 1. Убедитесь, что модель подготовлена

В каталоге `backend/artifacts/current` должны находиться:

```text
manifest.json
metrics.json
model.cbm
```

В текущей локальной сборке эти файлы уже созданы. Если их нет, сначала выполните раздел [Переобучение модели](#переобучение-модели).

### 2. Соберите и запустите приложение

Откройте PowerShell в корне проекта и выполните:

```powershell
docker compose up --build -d --wait
```

После успешного запуска доступны:

- веб-интерфейс: <http://127.0.0.1:8088>;
- документация API: <http://127.0.0.1:8000/docs>;
- проверка состояния: <http://127.0.0.1:8000/api/health>.

Открыть интерфейс из PowerShell можно командой:

```powershell
Start-Process http://127.0.0.1:8088
```

Проверить состояние контейнеров:

```powershell
docker compose ps
```

Ожидаемое состояние обоих сервисов — `healthy`.

### 3. Выполните анализ

1. Откройте веб-интерфейс.
2. Выберите или перетащите CSV-файл.
3. Нажмите **«Запустить анализ»** и дождитесь завершения.
4. Проверьте сводку, предупреждения, метрики и записи с максимальным риском.
5. Перейдите в **«Рискованные записи»**, чтобы применить фильтры, изменить порог и открыть подробную карточку записи.
6. Используйте **«Качество модели»** для просмотра метрик и матрицы ошибок, если файл содержит корректный `GB_flag`.
7. Используйте **«Качество данных»**, чтобы посмотреть допустимые отклонения и технические значения.
8. Нажмите **«Скачать CSV»** для полного отчёта или **«Только ручная проверка»** для записей выше текущего порога.
9. Нажмите **«Завершить сессию»**, чтобы удалить загруженный файл, результаты и уведомления.

### 4. Остановите приложение

```powershell
docker compose down --remove-orphans
```

Загруженные файлы, SQLite-сессии и отчёты находятся во временной файловой системе контейнера `tmpfs`. Постоянный Docker volume для них не создаётся, а после остановки контейнера временные данные исчезают.

## Требования к CSV

Файл должен:

- иметь расширение `.csv`;
- быть сохранён в UTF-8 или UTF-8 с BOM;
- использовать `;` или `,` в качестве разделителя;
- содержать строку заголовков без пустых и повторяющихся названий;
- соответствовать признакам модели хотя бы на 80%;
- обязательно содержать критические признаки модели.

Полный ожидаемый набор признаков и их профили находятся в [`backend/artifacts/current/manifest.json`](backend/artifacts/current/manifest.json).

Колонка `GB_flag` необязательна при анализе:

- если она отсутствует, модель рассчитает риски, но метрики качества будут недоступны;
- если она присутствует и содержит бинарные значения `0` и `1`, приложение дополнительно рассчитает ROC-AUC, PR-AUC, Gini, KS, precision, recall и confusion matrix;
- `GB_flag` никогда не используется как входной признак при прогнозировании.

Лишние колонки сохраняются в итоговом отчёте, но не влияют на прогноз. Допустимые пропуски заполняются по правилам, сохранённым при обучении. Неизвестные категории и заметные изменения качества данных показываются пользователю как предупреждения.

## Что содержится в результате

Для каждой строки приложение возвращает исходные поля и добавляет:

- `risk_probability` — вероятность риска от `0` до `1`;
- `risk_level` — уровень риска;
- `requires_review` — необходимость дополнительной проверки при выбранном пороге;
- `explanation_factors` — наиболее значимые факторы SHAP.

Результаты по умолчанию отсортированы от максимального риска к минимальному.

Дополнительная выгрузка «Только ручная проверка» содержит только записи, у которых `risk_probability` не ниже текущего порога. Изменение порога влияет на решение о ручной проверке, но не переобучает модель.

## Конфиденциальность и жизненный цикл данных

- браузер обращается только к локальному `/api` через Nginx;
- frontend не содержит внешних аналитических, рекламных или облачных интеграций;
- исходный CSV, SQLite-сессия и сформированные отчёты хранятся во временной файловой системе backend-контейнера;
- завершение сессии удаляет данные выбранного анализа;
- остановка контейнеров удаляет оставшиеся временные данные `tmpfs`;
- модель формирует приоритет проверки, но не блокирует клиента и не принимает автоматическое решение.

## Переобучение модели

Текущая модель является обучаемой с учителем: для переобучения нужен CSV с бинарной целевой колонкой `GB_flag`.

Требования для локального обучения:

- Python 3.11–3.13;
- исходный обучающий CSV;
- свободная оперативная память и место на диске.

Создайте окружение и установите backend с зависимостями:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".\backend[test]"
```

Запустите обучение на образце из каталога `data`:

```powershell
.\.venv\Scripts\python.exe -m app.training.train `
  --input "data\Dataset(Лист1).csv" `
  --output "backend\artifacts\current"
```

Обучение создаёт `model.cbm`, `manifest.json` и `metrics.json`. После него пересоберите backend и перезапустите приложение:

```powershell
docker compose build backend
docker compose up -d --wait
```

## Запуск без Docker для разработки

Понадобятся Python 3.11–3.13, Node.js 22 и npm.

Установите зависимости из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".\backend[test]"
npm ci --prefix frontend
```

Запустите backend в первом окне PowerShell:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app `
  --app-dir backend `
  --host 127.0.0.1 `
  --port 8000
```

Запустите frontend во втором окне:

```powershell
npm --prefix frontend run dev
```

Интерфейс разработки будет доступен по адресу <http://127.0.0.1:5173>. Vite автоматически перенаправляет запросы `/api` на backend.

## Возможные проблемы

### Статус `degraded` или ошибка `model_unavailable`

Проверьте наличие трёх файлов в `backend/artifacts/current`. Если модель была переобучена после сборки Docker-образа, выполните:

```powershell
docker compose up --build -d --wait
```

### CSV отклонён

Проверьте кодировку UTF-8, разделитель, уникальность заголовков и наличие критических признаков. Интерфейс показывает конкретные отсутствующие колонки и другие причины отклонения.

### Порты уже заняты

Приложение использует локальные порты `8088` и `8000`. Остановите программу, которая занимает нужный порт, либо измените привязку портов в `docker-compose.yml`.

### Большой файл обрабатывается медленно или не хватает памяти

Анализ 100 000 строк размером около 150 МБ в контрольной конфигурации занял примерно 3 минуты и потребовал до 2.7 ГБ памяти backend-контейнера. Фактическое время зависит от процессора и диска. Не запускайте одновременно несколько файлов, близких к максимальному размеру: временное хранилище backend ограничено 1 ГиБ.

### После обновления кода интерфейс не изменился

Пересоберите frontend-контейнер и дождитесь состояния `healthy`:

```powershell
docker compose build frontend
docker compose up -d --no-deps --force-recreate --wait frontend
```

Затем обновите страницу браузера. Пользовательские CSV при пересборке frontend не передаются во внешние сервисы.
