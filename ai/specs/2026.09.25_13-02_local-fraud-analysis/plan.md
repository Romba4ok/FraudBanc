# План: Локальный анализ риска мошенничества по CSV

## Решение

### Архитектура приложения

Проект будет оформлен как локальный монорепозиторий из двух приложений, запускаемых через Docker Compose (R1):

- `frontend` — React, TypeScript и Vite. Интерфейс отвечает за загрузку файла, отображение прогресса, сводки, метрик, фильтруемой таблицы и скачивание отчёта.
- `backend` — FastAPI. API принимает CSV, проверяет размер и схему, запускает фоновый анализ, хранит состояние локальной сессии, отдаёт страницы результата и поток скачивания.

Frontend не получает весь результат целиком. После загрузки он получает `analysis_id`, опрашивает статус анализа и запрашивает только текущую страницу таблицы. API предоставляет операции создания анализа, чтения статуса и сводки, получения записей с сортировкой и фильтрами, скачивания отчёта и явного удаления сессии (R4, R15, R16, R19).

### Обработка CSV и временное состояние

Backend принимает только `.csv`, ограничивает тело загрузки 150 МБ и сохраняет его в уникальный временный каталог сессии. Разделитель определяется между `;` и `,` по заголовку и проверочным строкам. Заголовки очищаются от внешних пробелов, проверяются на пустые и повторяющиеся имена, после чего сопоставляются с manifest модели независимо от порядка (R4-R8).

Обработка выполняется порциями. Для каждой строки сохраняется исходный порядковый номер; если поддерживаемого идентификатора нет, формируется `record_id` на его основе. Дополнительные столбцы сохраняются в результате, но не передаются модели. `GB_flag`, если он есть, извлекается до формирования матрицы признаков и никогда не попадает в модель (R6, R9, R10, R12).

Результаты порций записываются во временную SQLite-базу с индексом по `risk_probability`. Она обеспечивает сортировку, фильтрацию, пагинацию и потоковую выгрузку без отправки всей таблицы в браузер. В памяти процесса хранится только реестр активных заданий и агрегированная сводка. Исходный CSV, SQLite и сформированный отчёт удаляются по запросу завершения сессии и при очистке просроченных сессий; при старте backend удаляет оставшиеся временные каталоги прошлых запусков (R15, R16, R19).

### Модель и обучение

Одна CatBoost-модель обучается отдельной CLI-командой на CSV с бинарным `GB_flag` (R2, R3). Команда выполняет стратифицированное разделение 70/30 с фиксированным seed. Исходная тестовая выборка не ребалансируется. Для обучения применяется взвешивание классов; категориальные коды передаются CatBoost как категории, а не непрерывные числа.

Одинаковый preprocessing используется при обучении и прогнозировании. Он включает:

- нормализацию заголовков;
- удаление полностью пустых признаков из набора модели;
- отдельные правила для `-`, пустых значений и отрицательных sentinel-значений в зависимости от типа признака;
- приведение числовых признаков и категорий к типам из manifest;
- обработку отсутствующих и неизвестных категорий;
- контроль обязательных признаков, доли пропусков, допустимых диапазонов и изменения распределений;
- исключение `GB_flag` и технических идентификаторов.

Артефакт версии модели состоит из `model.cbm`, `manifest.json` и `metrics.json`. Manifest хранит версию, список и типы признаков, критические поля, правила очистки, статистики обучающей выборки, границы предупреждений, уровни риска и порог ручной проверки. Сгенерированные бинарные артефакты не добавляются в Git, но их формат и расположение стабильны. Backend отказывается запускать прогноз при отсутствии или несовместимости артефактов (R2, R7, R8, R17, R20).

Порог ручной проверки выбирается на валидации с приоритетом полноты редкого положительного класса и сохраняется в manifest. Для текущего просмотра API принимает временный порог, не изменяя manifest. Уровни риска вычисляются по сохранённым границам и отображаются отдельно от бинарного флага проверки (R13, R17).

### Результат и объяснимость

CatBoost выдаёт `risk_probability`; native SHAP для CatBoost рассчитывается порциями. Для строки сохраняются 3-5 признаков с наибольшим абсолютным вкладом, направление влияния и безопасное отображаемое значение. Целевой признак и сведения других строк в объяснение не включаются (R13, R14).

Если вход содержит корректный бинарный `GB_flag`, backend рассчитывает Gini, KS, Accuracy, Precision, Recall, ROC-AUC, PR-AUC и матрицу ошибок на всём загруженном файле с текущим порогом. Без target блок метрик помечается как недоступный, а прогноз остаётся рабочим (R9-R11).

Итоговый CSV сохраняет исходные разрешённые столбцы и добавляет `record_id`, `risk_probability`, `risk_level`, `requires_review`, объясняющие факторы и предупреждения. Строки выгружаются по убыванию риска (R12-R16).

### Интерфейс

Интерфейс строится как одна локальная рабочая область: экран загрузки, состояние проверки/обработки, сводка анализа, предупреждения качества, метрики при наличии target и таблица результатов. Первый экран результата сразу показывает наиболее рискованные записи. Временный порог, фильтр уровня риска и пагинация управляют запросами к API (R4, R11, R15, R17).

Визуальная система следует `spec-kit-main/design.md`: глубокий тёмный фон, светлая типографика, ограниченный бронзовый акцент, строгая геометрия, ясная иерархия и минимум декоративного шума. Уровни риска имеют доступные текстовые подписи и не различаются только цветом (R18).

### Проверяемость

Backend разделяется на чистые сервисы чтения CSV, проверки схемы, preprocessing, прогнозирования, объяснений, метрик и временного хранилища. Зависимости FastAPI подменяются в тестах фиктивной моделью там, где не требуется реальный CatBoost. Отдельный интеграционный тест использует небольшой тестовый артефакт модели. Frontend проверяется Vitest и Testing Library; сборка TypeScript является обязательной проверкой. Контейнеры имеют healthcheck, а API не использует внешние сервисы (R21).

## Файлы и границы

### Можно менять

- `docker-compose.yml`: создать локальную конфигурацию frontend/backend и healthcheck для R1.
- `.gitignore`: создать или дополнить правилами для зависимостей, сборок, временных сессий, обученных бинарных артефактов и локальных секретов; не использовать принудительное добавление игнорируемых файлов.
- `README.md`: создать локальные команды запуска, обучения и проверок.
- `backend/pyproject.toml`: создать зависимости, CLI и настройки backend-тестов.
- `backend/Dockerfile`: создать контейнер FastAPI.
- `backend/app/__init__.py`: создать пакет приложения.
- `backend/app/main.py`: создать FastAPI-приложение, lifecycle и маршруты здоровья.
- `backend/app/api/**`: создать HTTP-маршруты анализа, статуса, результатов, скачивания и очистки.
- `backend/app/core/**`: создать конфигурацию лимитов, путей, CORS для локального frontend и загрузки модели.
- `backend/app/domain/**`: создать типы состояния анализа, предупреждений, метрик и публичных ответов API.
- `backend/app/services/**`: создать чтение CSV, проверку схемы, preprocessing, inference, SHAP, метрики, SQLite-сессии и очистку временных данных.
- `backend/app/training/**`: создать отдельную CLI-команду обучения, оценки и сохранения артефактов.
- `backend/artifacts/.gitkeep`: создать пустой маркер каталога артефактов.
- `backend/artifacts/**`: генерировать локальные model/manifest/metrics только командами обучения; не добавлять бинарные результаты в staging.
- `backend/tests/**`: создать unit и integration тесты backend.
- `frontend/package.json`, `frontend/package-lock.json`, `frontend/tsconfig*.json`, `frontend/vite.config.ts`, `frontend/eslint.config.js`, `frontend/index.html`: создать конфигурацию React-приложения и проверок.
- `frontend/Dockerfile`, `frontend/nginx.conf`: создать локальную сборку и проксирование API.
- `frontend/src/**`: создать приложение, API-клиент, компоненты загрузки, прогресса, сводки, метрик, фильтров, таблицы и стили.
- `frontend/tests/**`: создать тестовые настройки и сценарии интерфейса, если они не размещены рядом с компонентами.
- `ai/specs/2026.09.25_13-02_local-fraud-analysis/plan.md`: поддерживать технический план.
- `ai/specs/2026.09.25_13-02_local-fraud-analysis/tasks.md`: создать и обновлять очередь задач и доказательства проверок на следующих этапах.

### Нужно подтверждение

- Установка или загрузка зависимостей из сети, если локальный кэш их не содержит.
- Создание файлов вне перечисленных путей.
- Изменение публичной схемы API после того, как frontend начнёт её использовать.
- Добавление постоянной базы данных, внешнего сервиса, облачного развёртывания или авторизации.
- Commit, staging или push любых файлов.

### Нельзя менять

- `data/**`: исходные CSV, DOCX и PDF остаются неизменными и используются только как входные данные.
- `spec-kit-main/**`: инструкции и дизайн-референс остаются неизменными.
- `ai/specs/2026.09.25_13-02_local-fraud-analysis/spec.md`: согласованные требования не меняются в рамках plan/implement; смысловая правка требует возврата к specify.
- Другие каталоги внутри `ai/specs/**`, если они появятся.
- `.git/**` и история репозитория.

Любая неуказанная запись требует подтверждения. При пересечении границ действует более строгое правило.

- В образце 72 506 строк и 177 столбцов, 570 положительных `GB_flag` (около 0,786%), поэтому Accuracy сама по себе непоказательна. Используются стратификация, веса классов, PR-AUC, Recall, Gini и KS; тестовая выборка остаётся несбалансированной согласно заданию.
- В CSV нет идентификатора клиента. `record_id` формируется из исходной позиции строки и стабилен только внутри конкретной загрузки; он не объявляется постоянным идентификатором человека.
- В образце обнаружены пробелы в заголовках, два полностью пустых столбца, точные дубликаты, числовые коды категорий, высокая доля `-` и отрицательные значения в счётчиках. Единая таблица правил в manifest предотвращает расхождение обучения и inference; значения `-` не преобразуются глобально одним правилом.
- PDF описывает `SALARY`, но такого столбца нет в CSV. Он не считается обязательным признаком текущей модели, пока не появится в обучающем наборе и новой версии manifest.
- Новые CSV могут иметь неизвестные категории и drift. Неизвестные категории допускаются и фиксируются предупреждением; отсутствие критического признака или превышение границ совместимости блокирует прогноз, чтобы не выдавать внешне правдоподобный ненадёжный результат.
- Взвешивание классов может ухудшить калибровку вероятностей. Выбор порога и проверка калибровки выполняются на валидации; интерфейс обозначает результат как оценку риска, а не доказанный факт мошенничества.
- SHAP для 100 000 строк может быть дорогим. Расчёт выполняется порциями и сохраняет только 3-5 ведущих факторов; прогресс inference и explanation отображается отдельно.
- Локальная временная SQLite выбрана вместо постоянной БД: она обеспечивает сортировку и пагинацию, но удаляется вместе с сессией и не является архивом результатов.
- Файлы `data/**`, `spec-kit-main/**`, согласованная `spec.md` и Git запрещено изменять. Установка зависимостей, staging, commit и push не разрешены этим планом.
