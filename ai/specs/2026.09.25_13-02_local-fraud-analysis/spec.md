# Локальный анализ риска мошенничества по CSV

## Зачем

Нужен локальный веб-сервис для пользователя, который загружает CSV с анкетными и кредитными характеристиками заёмщиков и получает ранжированный результат анализа риска first-party fraud. Сервис должен использовать заранее обученную модель, не отправлять финансовые данные во внешние системы и в первую очередь показывать лиц, требующих ручной проверки.

Текущий файл `data/Dataset(Лист1).csv` служит обучающим образцом и примером ожидаемого формата. Каждая строка представляет одного заёмщика на дату выдачи кредита. Целевой признак `GB_flag` используется при отдельном обучении и оценке модели, но не передаётся модели как входной признак при прогнозировании.

## Требования

- R1: Система должна запускаться локально через Docker Compose и предоставлять веб-интерфейс на React, TypeScript и Vite, связанный с локальным API на FastAPI.
- R2: Рабочий прогноз должна выполнять одна заранее обученная модель CatBoost. Модель и весь необходимый для неё preprocessing должны загружаться из версионируемых локальных артефактов.
- R3: Обучение модели должно запускаться отдельной локальной командой на размеченном наборе данных с `GB_flag`; загрузка CSV через веб-интерфейс не должна переобучать или изменять рабочую модель.
- R4: Веб-интерфейс должен принимать CSV размером до 150 МБ и ориентировочно до 100 000 строк, показывать ход обработки и не требовать загрузки всей итоговой таблицы в браузер одновременно.
- R5: При загрузке система должна автоматически распознавать разделитель `;` или `,`, удалять внешние пробелы из заголовков и сопоставлять признаки независимо от порядка столбцов.
- R6: Дополнительные столбцы во входном CSV не должны блокировать анализ. Они должны сохраняться в выгружаемом результате, если это не нарушает ограничения безопасности и формата.
- R7: Отсутствующие признаки, неизвестные категориальные значения и специальные значения должны обрабатываться по правилам, сохранённым при обучении. Система должна показывать предупреждения о найденных отклонениях.
- R8: Если отсутствуют критические признаки либо структура и распределение данных выходят за допустимые границы совместимости модели, система должна остановить прогноз и показать конкретные причины отклонения файла.
- R9: Система должна принимать как CSV без `GB_flag`, так и CSV с `GB_flag`. Наличие целевого столбца не должно влиять на рассчитанные прогнозы.
- R10: `GB_flag` должен быть полностью исключён из входных признаков модели и использоваться только как целевое значение при обучении или как фактическое значение при оценке качества.
- R11: Для CSV с корректным `GB_flag` система дополнительно должна показывать Gini, Kolmogorov-Smirnov, Accuracy, Precision, Recall, ROC-AUC, PR-AUC и матрицу ошибок на исходном несбалансированном наборе.
- R12: Если во входном файле нет поддерживаемого идентификатора клиента или счёта, система должна создать стабильный для текущего файла `record_id`, позволяющий сопоставить результат с исходной строкой.
- R13: После анализа каждая строка должна получить вероятность риска от 0 до 100%, уровень риска, признак необходимости ручной проверки и от трёх до пяти основных факторов, повлиявших на результат.
- R14: Объяснение факторов должно рассчитываться совместимым с CatBoost методом SHAP и не должно использовать `GB_flag` или данные других строк как объясняющие признаки конкретной записи.
- R15: Таблица результатов по умолчанию должна быть отсортирована по убыванию вероятности риска, чтобы наиболее подозрительные лица находились в начале списка. Должны быть доступны фильтрация по уровню риска и просмотр с пагинацией.
- R16: Пользователь должен иметь возможность скачать полный CSV-отчёт, содержащий исходные разрешённые столбцы, `record_id`, вероятность, уровень риска, флаг проверки, объясняющие факторы и предупреждения по строке.
- R17: Порог ручной проверки должен определяться по результатам валидации обученной модели и храниться в её конфигурации. Пользователь должен иметь возможность временно изменить порог для текущего просмотра без переобучения и изменения сохранённой модели.
- R18: Интерфейс должен следовать тёмному минималистичному визуальному направлению из `spec-kit-main/design.md`, обеспечивая читаемость таблиц, ошибок и уровней риска.
- R19: Загруженные CSV и сформированные результаты должны обрабатываться только локально, храниться временно и удаляться после завершения пользовательской сессии. Постоянно можно хранить только модель, её конфигурацию, версию и обезличенные технические сведения об обработке.
- R20: Подготовка данных должна учитывать подтверждённые особенности образца: внешние пробелы в заголовках, числовые коды категорий, полностью пустые признаки, дубликаты, специальные маркеры отсутствия данных и невозможные отрицательные значения в счётчиках. Правила их обработки должны быть одинаковыми при обучении и прогнозировании.
- R21: Автоматические проверки должны подтверждать корректность разбора CSV, сопоставления схемы, исключения `GB_flag`, применения preprocessing, прогнозирования, сортировки, расчёта метрик, формирования отчёта и работы API на допустимых и ошибочных входных данных.

## Не входит

- Публичное или облачное развёртывание.
- Авторизация, роли и многопользовательский режим.
- Переобучение модели через веб-интерфейс.
- Автоматическое обучение на загруженном для анализа CSV.
- Логистическая регрессия, нейросетевая или unsupervised-модель.
- Постоянное хранение исходных финансовых данных и результатов анализа.
- Автоматическая блокировка клиента или принятие окончательного решения о мошенничестве без ручной проверки.
