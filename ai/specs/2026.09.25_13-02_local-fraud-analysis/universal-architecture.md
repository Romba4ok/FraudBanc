# Архитектурное ТЗ: универсальный локальный fraud-анализ

**Статус:** согласованная концепция 1.0  
**Дата:** 27.09.2026  
**Продукт:** Risk Ledger  
**Режим:** полностью локальное web-приложение

## 1. Цель

Расширить Risk Ledger от анализа одного CSV фиксированной схемы до локальной системы, которая принимает выгрузки из разных источников, самостоятельно распознаёт структуру данных, строит безопасный план обработки и запускает подходящий fraud-анализ.

Система решает две разные задачи:

1. **Риск клиента** — вероятность first-party fraud по анкете, кредитной истории и агрегированным характеристикам. Рабочая модель: CatBoost.
2. **Подозрительные операции** — поиск нетипичных денежных движений без обязательной готовой разметки. Рабочая модель: Isolation Forest в сочетании с детерминированными правилами и анализом связей.

Результат модели является сигналом для ручной проверки, а не доказательством мошенничества.

## 2. Поддерживаемые локальные источники

Первая версия принимает только файлы, загружаемые пользователем через сайт. Прямых подключений к работающим базам нет.

| Семейство | Форматы | Назначение |
|---|---|---|
| Табличные файлы | `.csv` | анкеты, агрегаты, транзакции |
| SQL-выгрузки | `.sql` | дампы PostgreSQL, MySQL и Microsoft SQL Server |
| Локальная SQL-база | `.sqlite`, `.sqlite3`, `.db` | таблицы и связи SQLite |
| NoSQL-выгрузки | `.json`, `.jsonl`, `.ndjson` | документы и потоки документов |
| MongoDB | `.bson` | локальный BSON-дамп коллекции |

Ограничение первой версии: до 500 МБ на файл и до 1 000 000 логических записей. Обработка выполняется потоково или порциями. Весь набор не должен одновременно загружаться в память или браузер.

## 3. Основной процесс

1. Пользователь загружает один локальный файл.
2. Backend проверяет расширение, сигнатуру, размер и безопасность.
3. Адаптер источника строит инвентаризацию таблиц, коллекций, полей, типов, объёма и временного диапазона.
4. Система определяет сущности: клиент, счёт, договор, операция, получатель, устройство и другие поддерживаемые роли.
5. Семантический слой сопоставляет исходные поля с каноническими признаками.
6. Планировщик выбирает основную таблицу или коллекцию, связи, период, преобразования и аналитические профили.
7. Пользователь видит понятный план без технических имён полей и запускает анализ.
8. Выполняются проверка качества, построение признаков, прогноз, объяснение и формирование результатов.
9. Наиболее подозрительные клиенты и операции показываются первыми.
10. Пользователь проверяет сигналы, назначает статус расследования, добавляет комментарий и выгружает результат.
11. После завершения сессии исходный файл и временные результаты удаляются.

## 4. Автоматический выбор профиля

- При обнаружении анкеты, кредитной истории или агрегированных характеристик запускается профиль риска клиента.
- При обнаружении операций, суммы, времени и участников запускается профиль подозрительных операций.
- Если присутствуют оба набора, запускаются оба профиля, а результаты связываются по клиенту или счёту.
- Если обязательная семантика не распознана с достаточной уверенностью, система не угадывает и останавливает соответствующий профиль с понятным перечнем недостающих данных.

## 5. Канонический слой данных

Исходные схемы не передаются напрямую моделям. Между источником и моделями существует версионируемая каноническая схема:

- идентификаторы сущностей;
- характеристики клиента;
- кредитные показатели;
- агрегаты просрочек и долговой нагрузки;
- дата, время, сумма и валюта операции;
- отправитель, получатель, счёт и канал;
- устройство, география и дополнительные контекстные признаки;
- целевые метки, если они присутствуют;
- происхождение и качество каждого рассчитанного признака.

Для каждого канонического поля сохраняются исходное поле, преобразование, уверенность, версия словаря и причина сопоставления. Эти технические сведения доступны только в диагностическом JSON и не показываются в основном интерфейсе.

## 6. Анализ транзакций

Система должна находить как минимум:

- необычно крупные суммы;
- резкий рост частоты операций;
- серии переводов за короткое время;
- дробление суммы;
- нового или нетипичного получателя;
- ночные и необычные по времени операции;
- множество отправителей одному получателю;
- циклические переводы;
- быстрый вывод поступивших средств;
- активность после длительного бездействия;
- несоответствие текущей операции обычному поведению клиента.

При одном месяце используется сравнение с когортой внутри среза. При наличии истории дополнительно строится персональная базовая линия клиента. Интерфейс явно сообщает применённый режим сравнения.

## 7. Обучение и накопление опыта

- Текущий `data/Dataset(Лист1).csv` используется для профиля риска клиента и переобучения CatBoost на `GB_flag`.
- Этот файл не является журналом отдельных транзакций.
- До появления реальной обезличенной транзакционной выгрузки профиль операций разрабатывается на синтетическом наборе, явно помеченном как тестовый.
- Isolation Forest обучается без учителя на допустимой выборке операций.
- Семантический словарь локально накапливает безопасные соответствия имён, типов и преобразований.
- Рабочая fraud-модель не обучается на собственных прогнозах.
- Статусы «Мошенничество подтверждено» и «Ложная тревога» формируют контролируемую разметку для будущих кандидатных моделей.
- Новая версия модели сначала сравнивается с рабочей на фиксированной контрольной выборке и не активируется автоматически.

## 8. Хранение и приватность

Постоянно разрешено хранить только:

- обезличенный семантический словарь;
- правила преобразования и версии канонической схемы;
- подтверждённые метки расследований в обезличенном виде;
- артефакты и метрики версий моделей;
- журнал изменения словаря и моделей.

Исходные файлы, полные значения записей и сформированные рабочие таблицы хранятся только во временном каталоге сессии. ФИО, карты, счета, телефоны и документы маскируются на frontend по умолчанию.

## 9. Выгрузки

- полный CSV результата;
- CSV записей для ручной проверки;
- CSV подозрительных операций;
- CSV связей «клиент — счёт — получатель — операция»;
- CSV качества распознавания;
- JSON технического плана и происхождения признаков.

PDF в первую версию не входит.

## 10. Границы первой версии

Не входят:

- прямое подключение к PostgreSQL, MySQL, SQL Server или MongoDB;
- исполнение загруженного SQL-кода;
- облачная отправка данных или внешняя LLM;
- автоматическая блокировка клиента или операции;
- незаметная замена рабочей модели;
- обещание корректного анализа произвольной схемы при отсутствии обязательной семантики;
- использование синтетических метрик как доказательства качества на реальных транзакциях.

## 11. Общие критерии приёмки

1. Каждый поддерживаемый формат проходит безопасную инвентаризацию.
2. Прогресс и текущий этап отображаются для любого размера файла.
3. Основной интерфейс не показывает технические имена исходных переменных.
4. Нераспознанные обязательные данные останавливают только зависимый профиль с конкретным объяснением.
5. SQL-дамп анализируется без исполнения потенциально опасных команд.
6. Результаты отсортированы по убыванию риска.
7. Для каждого сигнала доступны понятные причины.
8. Исходные данные не покидают локальное окружение.
9. После удаления сессии временные данные отсутствуют.
10. Автоматические тесты покрывают адаптеры, семантическое сопоставление, модели, API и frontend.
