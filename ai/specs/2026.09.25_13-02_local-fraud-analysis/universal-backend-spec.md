# Техническое задание: backend универсальных источников

**Статус:** согласованная концепция 1.0  
**Основа:** существующий FastAPI backend Risk Ledger

## 1. Назначение

Backend безопасно принимает локальный файл, определяет его формат, извлекает структуру и данные, строит каноническое представление, оркестрирует два аналитических профиля и отдаёт результаты порциями.

## 2. Компоненты

1. Upload Gateway.
2. File Type Detector.
3. Source Adapter Registry.
4. Schema Profiler.
5. Semantic Mapping Service.
6. Analysis Planner.
7. Canonical Transformation Pipeline.
8. Client Risk Pipeline.
9. Transaction Anomaly Pipeline.
10. Relationship Builder.
11. Result Store.
12. Feedback Store.
13. Model Registry.
14. Export Service.
15. Session Cleanup Service.

Каждый компонент имеет отдельный интерфейс и unit-тесты.

## 3. Адаптеры источников

Все адаптеры возвращают общий контракт: список наборов данных, поля, типы, количество записей, пример обезличенных значений, статистику пропусков, возможные ключи, связи и временные поля.

### 3.1. CSV

- автоматическое определение разделителя и кодировки;
- очистка заголовков;
- потоковое чтение;
- обнаружение строк с отличающейся шириной;
- сохранение исходного порядка строк.

### 3.2. JSON, JSONL и NDJSON

- поддержка массива документов и построчных документов;
- безопасное разворачивание вложенных объектов с ограничением глубины;
- массивы не преобразуются в бесконтрольное декартово произведение;
- неоднородные документы профилируются как объединённая схема.

### 3.3. SQLite

- файл открывается только для чтения;
- запрещены расширения, attach и запись;
- инвентаризируются таблицы, представления, ключи и индексы;
- системные таблицы не становятся бизнес-сущностями.

### 3.4. SQL-дампы

- дамп никогда не исполняется напрямую;
- поддерживаемые данные извлекаются из безопасного подмножества `CREATE TABLE`, `INSERT`, `COPY` и эквивалентных batch-вставок;
- диалект определяется между PostgreSQL, MySQL и SQL Server;
- DDL используется только для восстановления схемы;
- процедуры, функции, триггеры, команды ОС, сетевые операции, управление пользователями и неизвестные конструкции отклоняются или игнорируются по строгой политике;
- каждое решение парсера фиксируется в отчёте импорта.

### 3.5. BSON

- потоковое чтение документов;
- распознавание BSON-типов и ObjectId;
- ограничение глубины и размера одного документа;
- невозможность исполнения JavaScript и server-side выражений.

## 4. Инвентаризация и профилирование

Для каждого набора вычисляются:

- количество строк или документов;
- типы и доля пропусков;
- приблизительная уникальность;
- кандидаты на идентификаторы и внешние ключи;
- минимальные и максимальные даты;
- распределение числовых значений;
- ограниченный набор категорий;
- признаки персональных данных;
- предупреждения качества;
- происхождение поля.

Профилирование больших наборов выполняется порциями. При использовании выборки это явно отражается в плане.

## 5. План анализа

План имеет версионируемый JSON-контракт и содержит:

- источник и найденный диалект;
- выбранные наборы данных;
- сущности и связи;
- канонические поля и преобразования;
- внутреннюю уверенность сопоставления;
- временной диапазон;
- доступные аналитические профили;
- режим сравнения транзакций;
- блокирующие причины и предупреждения;
- ожидаемые этапы и оценки объёма.

План создаётся до inference и сохраняется в каталоге сессии.

## 6. Обработка и прогресс

Каждый анализ имеет конечный автомат состояний:

`uploaded → inspecting → mapping → planning → validating → transforming → client_scoring → transaction_features → transaction_scoring → relationships → explaining → exporting → ready`.

Дополнительные состояния: `partially_ready`, `failed`, `cancel_requested`, `cancelled`, `deleted`.

Статус содержит общий процент, процент этапа, счётчик обработанных записей, предупреждения и активные профили. Отмена проверяется между порциями и не оставляет неполных результатов как готовые.

## 7. Временное и постоянное хранение

- каждый анализ получает изолированный временный каталог;
- нормализованные и результирующие данные хранятся во временной SQLite или совместимом локальном columnar-представлении;
- пагинация и фильтры выполняются на backend;
- исходный файл и временные результаты удаляются по завершению сессии и TTL-cleanup;
- постоянный словарь и feedback store не содержат исходных значений персональных данных;
- операции записи выполняются атомарно;
- при старте удаляются незавершённые временные сессии прошлого запуска.

## 8. API

Минимальный контракт:

- `POST /api/analyses` — загрузить файл;
- `GET /api/analyses/{id}/status` — этапы и прогресс;
- `GET /api/analyses/{id}/inventory` — понятная инвентаризация;
- `GET /api/analyses/{id}/plan` — план анализа;
- `PATCH /api/analyses/{id}/plan` — изменить только разрешённый период;
- `POST /api/analyses/{id}/run` — запустить утверждённый план;
- `POST /api/analyses/{id}/cancel` — запросить отмену;
- `GET /api/analyses/{id}/summary` — общий результат;
- `GET /api/analyses/{id}/clients` — клиенты с пагинацией и фильтрами;
- `GET /api/analyses/{id}/transactions` — операции с пагинацией и фильтрами;
- `GET /api/analyses/{id}/relationships` — ограниченный граф или таблица связей;
- `GET /api/analyses/{id}/entities/{type}/{entity_id}` — карточка сущности;
- `PATCH /api/analyses/{id}/investigations/{entity_id}` — статус и комментарий;
- `GET /api/analyses/{id}/exports/{kind}` — потоковая выгрузка;
- `DELETE /api/analyses/{id}` — удалить сессию.

Ответы не раскрывают исходные технические имена полей, кроме диагностического экспорта.

## 9. Безопасность

- проверка расширения и сигнатуры;
- защита от zip bomb не требуется до появления архивов, архивы отклоняются;
- лимиты размера файла, строки, документа, вложенности и количества полей;
- запрет path traversal;
- SQLite только read-only;
- SQL только парсится;
- JSON/BSON не выполняют встроенный код;
- CSV formula injection нейтрализуется при экспорте;
- ошибки не возвращают секретные пути и полные значения;
- все пользовательские идентификаторы проходят нормализацию и маскирование;
- внешние HTTP-запросы отсутствуют.

## 10. Производительность

- лимит 500 МБ и 1 000 000 записей;
- порционная обработка с настраиваемым batch size;
- ограниченная очередь локальных задач;
- индексы результата по риску, статусу, времени и сущности;
- скачивание формируется потоково;
- граф связей запрашивается только для выбранного подмножества;
- нагрузочный тест фиксирует время и пиковую память для контрольных файлов.

## 11. Backend-критерии приёмки

1. Все адаптеры реализуют единый контракт.
2. Опасный SQL не исполняется.
3. Срез данных из SQL-дампа доступен для анализа.
4. Вложенные NoSQL-документы преобразуются воспроизводимо.
5. План строится до запуска модели.
6. Анализ можно отменить.
7. Частичный успех двух профилей представлен корректно.
8. Пагинация стабильна и наиболее рискованные записи идут первыми.
9. Экспорт защищён от формульной инъекции.
10. Удаление сессии подтверждено файловой проверкой.
